# ETF report evidence (UPDATEV2-0018)

The ETF report path is a local-first evidence projection for exactly three
English document kinds: prospectus, annual report and half-year report.  A
typed `EtfReportImportRequest` is the only v2 import authority.  It binds the
instrument, exact kind, narrow source authority, optional identity
expectations, source URL and configured universe IDs.

Import retains bytes once under `data/raw/etf_reports/<sha256>.pdf`, verifies
the expected checksum before decoding, then decodes that retained snapshot in
a spawned child. A checksum-specific guard is held through decode and atomic
publication; every re-import validates the retained bytes, and the snapshot is
reasserted in the report/registry/conflict atomic group. The child API performs
its own bounded streaming size/checksum preflight before spawn or fallback and
has a hard timeout and a platform-specific hard
memory cap (POSIX `RLIMIT_AS`; Windows Job Object process-memory limit).  Page
count is observed before extraction, and page, page-text, total-text and
field-excerpt bounds fail closed.  No retry, network access, OCR, model or
generative extraction is involved.

Every structured field has status, value, candidates, page provenance, the
matched label and a bounded excerpt.  Required structural fields are
`fund_name`, `ISIN`, `document_date` and `legal_structure`; annual and
half-year reports additionally require `reporting_period_end`.  Unsupported
language/template, malformed identity dates, identity mismatch, missing
required fields, decode failure and resource limits remain explicit failed
registry states and are never `available`.

The registry and report store share a v2 source identity derived from
instrument, `prospectus_report`, exact kind, checksum, document date (or
missing) and source authority.  Parser version and plugin IDs are persisted in
the extraction row.  Registry v1 IDs and reads remain compatible, while the
generic document importer rejects `prospectus_report`.

Report extraction rows retain immutable non-review fields under an
`extraction_sha256` fingerprint.  Typed reviews provide only source ID,
fingerprint, reviewer, decision and optional note; review time is generated by
the store. The requested registry path must resolve exactly to the extraction's
stored registry path. Every history entry carries the extraction fingerprint;
the full timestamp chronology and top-level projection of its final entry are
validated on read and before append. Verification requires a complete, page-supported extraction with
no unresolved conflict.  Review is advisory only: `score_eligible` and
`execution_allowed` remain false.

The bounded conflict store compares the latest non-rejected report of each
kind.  Stable fields are compared across kinds; time-varying optional fields
are compared only for the same reporting period.  Both source identities,
kinds, dates, values and pages are retained as unresolved manual-review rows;
no canonical value is selected.  Conflicted evidence is ineligible and the
store is recomputed after each import or review. Eligibility is recomputed in
both directions from current verification, verifiability, exact registry
binding and conflicts, so rejecting a conflicting extraction can restore only
still-valid verified evidence.

All registry read-modify-write publishers use one exported persistent registry
guard. Lock order is registry then disclosure/conflict stores (with the report
snapshot guard outside that sequence), and already-locked private publication
paths avoid recursive acquisition and lost concurrent updates.

The Trust Evidence page exposes the three report kinds, field values,
plugins, pages, checksums, authority, parser/review status, fingerprints,
typed Verify/Reject controls and the conflict table.  This surface does not
feed ISSUE-0104 structural scoring or any execution authority.
